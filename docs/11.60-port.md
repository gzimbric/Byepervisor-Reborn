# Firmware 11.60 port

## Status

The regular/non-Pro PS5 path is hardware validated. The PS5 Pro path is
intentionally refused until its hypervisor heap range and VMCB population are
surveyed with the same read-only procedure.

The validated lifecycle is the normal Byepervisor-Reborn workflow:

1. Run `byepervisor_reborn.elf` from elfldr.
2. The payload updates the guest kernel text mappings and arms the one-shot
   `startup_mp` hook.
3. Enter rest mode and resume.
4. The startup AP locates and changes the live GameOS VMCBs.
5. The resumed payload requires a verified 16/16 result before reading ktext.

## Why offsets were not sufficient

The kernel part of the port was offset-driven. The 11.60 `startup_mp` call,
init vector, IDT/TSS symbols, data cave, page-map store, and reachable chain
gadgets were derived and then exercised on hardware.

The original AP payload also relies on hypervisor runtime globals for the heap
and `pcpus`. Applying the corresponding 13.x-style offsets to the 11.60 hvcore
image located the expected objects in the image, but both values were zero
during the startup AP execution window. The offsets were not wrong as image
locations; their runtime state was unavailable at the moment the exploit needs
it. That makes a literal offset-only port insufficient on 11.60.

## Read-only discovery

The bring-up payload first located the 11.60 hvcore image from architectural
VMRUN anchors and then surveyed the hypervisor heap without writes. It found 32
structurally valid VMCB-like pages in two groups. The 16 GameOS VMCBs were:

```text
0x62a57000, 0x62a59000, ... , 0x62a75000
```

The injected startup AP was uniquely identifiable at `0x62a59000` by the CR3
and RIP supplied by the resume chain. Its live ASID identified the 16-entry
GameOS set.

## Production safety gates

The 11.60 AP scans only the regular console's bounded hypervisor heap window,
`[0x62a00000, 0x63800000)`. It performs no hypervisor write unless all of these
checks pass:

- exactly one VMCB matches the injected AP's CR3 and RIP;
- that VMCB has nested control `9`, a valid ASID, and aligned in-range NPT and
  IOPM addresses;
- exactly 16 structurally valid VMCBs share the live GameOS ASID;
- the unique self VMCB is a member of that 16-entry set.

Only after those gates pass does it clear nested-paging enable at VMCB `+0x90`
and clear VMCB clean bits at `+0xc0`. It then reads every selected VMCB back and
requires `written=16`, `verified=16`, and `error=0`. The outer payload refuses
the post-wake ktext read unless that exact result and the pre-rest page-table
preparation marker are both present.

## Ordering bug found during bring-up

An early diagnostic finalizer changed the guest kernel text page-table entries
after the sleep/resume transition and immediately tried to read ktext. That
crashed the console even though the VMCB strike itself had succeeded.

The upstream ordering is essential:

```text
prepare guest page tables -> arm hook -> sleep/resume -> AP VMCB strike -> read ktext
```

With that ordering, the port read and streamed the full 11.60 kernel text span:

- virtual base observed: `0xffffffff99ee0000`
- length: `0xD30000` (13,828,096 bytes)
- validation dump SHA-256:
  `0e3439b5b4d249010fede6ad31d8969e01ad56824d3f80554545745a8f7260d5`

## Other 11.60-specific changes

- `pop r8` is not available within 11.60 kernel `.text`. Hook stores use
  `pop rax; mov [rcx], rax` instead.
- Kernel text page-table walking stops at a 2 MiB PDE leaf instead of treating
  its physical frame as a page-table page.
- The production proof no longer writes `0x41414141` into kernel text.
- The AP payload is `0x486` bytes in the validated build, below the `0xF00`
  staging limit, and contains no VMRUN, VMMCALL, control-register, debug-register,
  or MSR instructions.
